## 1. 現在の構成

| 項目 | 内容 |
|---|---|
| サーバ | `server.py`（標準ライブラリのみ / `ThreadingHTTPServer`） |
| フロント | `static/index.html` 単一ファイル（Chart.js はCDN） |
| タブ | ライブ / サーチ / 個ラン |
| データ元 | gbfdata API（`https://gbfdata.com/api`） |
| ローカル起動 | `python3 server.py` → `localhost:8930` |
| ホスティング | Render 無料プラン（512MB / 15分アイドルでスリープ、復帰約50秒） |

### 重要な制約・ハマりどころ

- **`User-Agent: Mozilla/5.0` ヘッダが必須**。素の urllib は 403 Forbidden になる。
- **`protocol_version = "HTTP/1.1"` が必須**。既定の HTTP/1.0 だと Render のプロキシが接続を
  再利用したときに `x-render-routing: no-server` で約50%が404になる。全レスポンスに
  `Content-Length` を付けること。
- gbfdata は**毎時のスナップショットのみ**保持（`07:00`〜`24:00`）。`:20` `:40` は存在しないので
  20分刻みのグラフは作れない。
- 予選の時刻表記は 20:00〜30:00（30:00 = 翌6:00）。予選は深夜も稼働する。
- **本戦は7時〜24時**。24時以降は貢献度に反映されない。
- `day_of`: 1=予選1日目, 2=予選2日目, 3=インターバル, 4〜7=本戦1〜4日目
- 個人の `point` はイベント累積、団の `today_point` はその日ぶん。
- マッチング: Day1/4=大枠、Day2/3=前日の貢献度。
- `users/rankings` の `per_page` は**500まで有効**（1000は不可）。
- ランキングの深度は約200,500位まで。
- **個人の時刻毎データを直接返すAPIは存在しない**（`/users/{uid}/histories` は日別のみ）。
  そのため時刻毎の個人順位はランキングページを走査して特定する必要がある。

## 2. 個ランの時刻毎(1H)の探索（2026-07-30）

### 表示モード

**「概要(日別)」＋「各日(1H)」の8項目のみ。** 全期間(1H)は走査量が多く負荷が大きいため
2026-07-30に**廃止**した（サーバ59行・フロント41行を撤去）。
日程に無い `day` 値（廃止した `day=all` の古いブックマークやキャッシュ）は
**概要にフォールバック**させる。これを忘れると `do` が `None` になり
`ev.get(do - 1)` で `TypeError` を返す（実際に本番で発生させた）。

### 探索アルゴリズム（`koran_hourly`）

個人の時刻毎データを返すAPIが無いので、時刻ごとにランキングページを走査して本人を探す。
段階を追って、簡単な人は早く終わり、難しい人だけ時間をかける構成にしている。

1. `users/rankings` の `per_page` を 500 に（`PAGE = 500`）。リクエスト数が約1/5。
2. **①アンカー**: 均等な5点を `max_pages=14` で先に実測（並列8）。
3. **②補間**: 残りはアンカー間の順位を線形補間して `max_pages=8` の狭い範囲で探す。
4. **③総なめ**: それでも取れない時刻は `find_user_sweep` で**1位から順位帯を総なめ**。
   まず数点だけ総なめして足場を作り、間は `max_pages=20` の補間で埋め、
   最後の取り残しだけ再び総なめする。
   総なめはページを**24枚ずつ並列**に見て、見つかった時点で打ち切る
   （`find_user` は1枚ずつ順に見るので、86枚目で当たる場合に86回の逐次通信になり遅い）。
5. キャッシュを `uid -> (点数, 順位, 時速)` の辞書に畳む（`_slim_users`）。
   500件ぶんのdictを持たずに済み、`find_user` も走査せず直接引ける。
6. **先読み**（`prewarm_loop` / 毎時4分）で本人の**当日ぶん**を最優先で温め、`_pinned` に
   入れて他の団員を検索してもLRUで押し出されないよう保護。
   全期間の廃止に合わせて7日ぶん→1日ぶんに絞り、gbfdataへの毎時アクセスを約1/7にした。
7. **本戦(day_of 4〜7)は24時以降を走査しない**。予選・インターバルは末尾のボーダーが
   動いたかで判定して落とす（日種別の決め打ちを避け、次回開催にも自動追従）。

### ⚠️ 最重要の教訓: 取得漏れを直前値で埋めると「誤った数値」になる

「取れない時刻は直前値を引き継ぐ」だけの実装にすると、**取得漏れと本当の稼ぎ0が
区別されず、漏れが『稼ぎ0』として固定表示される**。

実害の例（さくらえび・本戦1日目）:

| 時刻 | 埋めて表示していた値 | 実際の値 |
|---|---|---|
| 8時 | 5.6億 / 42677位 / 時速0.0 | **11.1億 / 16536位 / 時速5.5** |
| 12時 | 5.6億 / 42677位 | **17.3億 / 11911位** |
| 20時 | 5.6億 / 42677位 | **17.6億 / 23875位** |

18時刻のうち実測できていたのは7時と24時だけで、17時間ぶんの数値を作ってしまっていた。
**異常の見分け方: 順位が何時間も1桁も動かない。** 本人が止まっていても他人が伸びれば
順位は動くので、順位が完全に同一なら実測ではない。

原因は**順位が非単調に動く**こと。さくらえびは `7時 42677位 → 9時 8338位 → 24時 34713位`。
朝に一気に伸ばして順位が3万位以上ジャンプし、その後は止まって抜かれ続ける。
順位の連続性を前提にした補間では原理的に届かない。だから③の総なめが必要。

### 初回時刻の時速

先頭を一律 0.0 にすると**誤り**。予選1日目20時は2000位が既に0.8億あるのに0.0となり、
累積グラフと時速グラフが食い違う。
`speed(cum, prev0)` で **prev0 = 前日の最終値**を「1つ前の時刻」として使う
（ボーダーは `user_border_hourly(raid, prev_date)` の最終値、本人は `base_cum`）。

| 日程 | 初回時刻の時速 | 理由 |
|---|---|---|
| 予選1日目 20時 | 0.8（=累積そのもの） | イベント開始＝0からの増分 |
| 予選2日目 7時 | 0.4 | 前日30時(=6時)から1時間ぶん |
| 本戦1日目 7時（本人） | 0.0 | 24時〜7時は稼ぎなし |

`base_cum` は**必ず `round(x, 1)` で表示と同じ桁に丸める**。丸め差で時速が `-0.0` になる。

### 実測（第83回・本戦1日目）

| メンバー | 想定順位帯 | 実測取得 | 所要（初回） |
|---|---|---|---|
| Laphis（本人） | 数千位 | 18/18 | 6.6秒（キャッシュ後2.5秒） |
| すなっ | 数千位 | 18/18 | 6.1秒 |
| 紅蘭 | 2〜3万位 | 18/18 | 15.3秒 |
| とくこ | 4万位台 | 18/18 | 27〜46秒 |
| さくらえび | 1〜4万位を大きく変動 | 18/18 | 58秒 |

メモリは147MB前後（上限約200MBで頭打ち、512MB枠に対して余裕あり）。
1日ぶんで gbfdata に約549リクエスト・9.6req/s。これ以上速くするのは相手サイトへの
負荷面で避ける。中位以下が遅いのは正確さとのトレードオフで、**速度優先に戻すと
誤った数値が出る**ので戻さない。

### 検証のやり方（必ずこの2本で行う）

1. **独立した全域スキャン**（1位〜200,500位を500刻みで総なめ）で真の値を取り、照合する。
   目視やアプリ自身の出力同士の比較では、上記の「埋めた誤り」を見逃す。
2. **グラフと表の突き合わせ**: `charts['#kSpdH'].data` / `charts['#kCumH'].data` を
   ブラウザで読み出して表のセルと数値比較し、さらに「時速＝累積の差分」を検算する。

### 試して逆効果だったので戻した案（再挑戦しないこと）

| 案 | 結果 |
|---|---|
| 逐次で順位を引き継ぐ（並列を捨てる） | 全期間39.6秒 / すなっ172秒 / 単日36秒 |
| アンカーを逐次化（5点だけ） | とくこ単日66秒 / 全期間134秒 |
| 点数から順位をlog-log推定（2000位と10万位を基準） | 紅蘭が125→76時刻に悪化、単日20秒 |
| 深追いの二分探索 `find_user_deep` | 単日3.2→10.1秒、紅蘭で24時刻欠損 |
| `max_pages` を大きく取る（60など） | 単日16.7秒に悪化 |
| 総なめを `find_user`（1枚ずつ逐次）で行う | さくらえび126秒。並列化して58秒 |

**教訓: 並列を捨てる案と、順位のヒント推定を凝る案はすべて悪化した。**
効いたのは「リクエスト数を減らす（per_page）」「走査対象を減らす（死に時間の除外）」
「先読み」「見つからない場合に総なめへ切り替える」。

## 3. メモリ超過(OOM)の対処

Renderから「exceeded its memory limit」通知。原因は `_cache` に上限がなく、
期限切れも掃除していなかったこと（1件38KBのランキング応答が蓄積）。

- `CACHE_MAX` + `_cache_put` でのLRU削除
- `slim=` で保存前に応答を間引く
- `per_page` と TTL の調整

現在は上限約200MBで頭打ち（512MB枠の約40%）。`_pinned` は `PIN_MAX = 600` で上限を持つ。

## 4. 主なUI仕様（ユーザー指定）

- 日程名は全て「予選1日目 / 予選2日目 / インターバル / 本戦1日目〜4日目」で統一。
- カード色: 自団=薄い青 / 相手=薄い赤 / 英雄(2000位)=薄い赤 / 10万位=薄い緑。
- 並び順: 当日貢献度 → 時速 → 参考情報 → 総合順位の推移。**勝率予想は最後**。
- 勝率は厳しめ（`ratio_winprob` の指数k=3.5。団1位級の比0.13で1%未満）。
- 本戦1・2日目は勝敗が付いたら抑える（翌日のマッチングと戦力温存のため）助言を出す。
- 時刻表示は素の値（24:00は「0時」ではなく「24時」、予選は25〜30時）。
- 見出し「時速（億・1H）」「(日程)（億単位）」「全期間の時速（億・1H）」「全期間（億単位）」。
- 個ランの表示モードは「概要(日別)」＋「各日(1H)」。**全期間(1H)は廃止**。
- 表に「—」を並べない。ただし**取得漏れを直前値で埋めてはいけない**（第2章の教訓）。
  実測がまだ無い先頭は0で埋める（順位だけは架空の値を入れず空欄のまま）。
- 自動更新は「更新時に自動更新」。gbfdataの毎時更新に追従（毎時3分、失敗時は3分おきに5回まで）。
- 開いた日の日程を自動選択。
- 団チャット通知用のコピペ文を最下部に出す（本戦・予選それぞれ）。

## 5. 運用メモ

- **pushは変更ごとに内容を報告して承認を得てから**行う（ユーザー指定）。
- 認証は専用のSSH鍵（`~/.ssh/config` の Host github.com で指定済）。
  **トークン・パスワード・認証コードは扱わない**（ユーザー自身が操作する）。
- リポジトリは**公開**なので、GAS Web AppのURL・団員の個人ID・スプレッドシートID・
  メールアドレスは絶対にコミットしない（push前に `git diff` で確認する運用）。
- 画面からファイルを直接アップロードすると、ローカルとリモートが分岐して push が
  拒否される。その場合は `git fetch` → 内容を確認 → `git reset --soft origin/main` →
  再コミットで、リモート履歴を消さずに最終版を載せられる。
- 次回（第84回）は開催が始まれば自動的にタブに追加される。
