# 個人ランキング追跡アプリ

決まった数人の個人貢献度を、**英雄(2000位)・10万位・15万位**のボーダーと並べて見るアプリ。
団の勝敗を見る本体アプリ（`/Applications/gbf/webapp`）とは別物で、コードも共有していない。

起動: `python3 /Applications/gbf/webapp/koran/server.py` → http://localhost:8931

## 1. 要になっている発見

gbfdata の `users/borders` は、**引数で順位も人も指定できる**。

```
/api/users/borders?raid_number=83&ranks=2000,100000,150000&user_ids=<ID1>,<ID2>,...
```

- `ranks` … 2000/10万位以外の任意の順位を返せる（**既定は2000と10万位だけ**）。15万位もこれで取れる
- `user_ids` … 指定した人の**時刻毎（順位つき）**が `users` に入って返る

⚠️ **本体アプリの個ランはこの引数を使っていない。** 順位帯を近傍探索（`find_user`）していて、
1人で20〜30秒かかる。こちらは**6人＋ボーダー3本で1.2秒**、1リクエスト。
本体アプリを速くしたくなったら、まずここを見ること。

## 2. 収録範囲と開催回の追従

- 時刻毎は**直近2回ぶんしか残らない**（第81回以前はJSONですらないものが返る）。
  だから選べるのは「最新回」と「その1つ前」の2つだけ。
- 最新回は `meta.latest_raid_number` をそのまま使う。`raid_number` を省いて叩けば最新回が返るので、
  **次の古戦場が始まれば何もしなくてもセレクタに増える**。ハードコードした開催回はどこにも無い。
- 開催直後は点が0件で返る。画面はそれを「まだありません」と出して落ちないようにしてある。

## 3. 追いかける人とライン

`server.py` の先頭2つを書き換えるだけで増減できる。

| 定数 | 中身 |
|---|---|
| `MEMBERS` | ユーザーIDだけ。**名前はgbfdataから取る**ので改名にも自動で追従する |
| `LINES` | `(順位, ラベル, 色)`。順位を足せばそのままボーダーが1本増える |
| `MCOLORS` | 人の線の色。人を足すときはここも足す（足りなければ循環する） |

## 4. 見る人の追加・削除

チップの右にある「＋ メンバーを編集」で、見る人をその場で足し引きできる。

⚠️ **保存先はブラウザ(localStorage、キー `koranUids`)。サーバには持たない。**
Renderは書いたファイルが消えるので保存先にできず、共有したいなら本体アプリと同じ
スプレッドシート保存(GAS)が要る。今は「その端末だけ」で足りるという判断。
**機種変更やブラウザを変えると初期メンバーに戻る**。

- 一覧が未保存なら環境変数 `KORAN_UIDS` の初期メンバーがそのまま出る。
  1人でも編集すると `koranUids` に入り、以後はそちらが使われる。
  「初期メンバーに戻す」は `koranUids` を消すだけ。
- 追加は名前かユーザーIDで検索する(`/api/search` がgbfdataを中継。ブラウザから直接は叩けない)。
  ⚠️ **同名が非常に多い**(「TOMO」で20件)。候補には**Lvと現在の貢献度・順位**を出し、
  貢献度の多い順に並べる。これが無いと別人を追加してしまう。
  候補の現在値は `user_ids` にまとめて渡す1リクエストで取っている。
- **上限15人**(`MAX_UIDS`)。URLの `uids` は誰でも書けるので、重複を潰して上限で切る。
  15人でも1.4秒・138KB。色は10色しか無いので16人目以降は色が巡る(だから上限も15)。
- **最後のひとりは外せない**。全部消すとサーバが初期メンバーに戻すので、
  「消したのに戻ってきた」という分かりにくい挙動になるため。

## 5. 画面の作り

本体アプリと同じ「判断バンド → 数値ストリップ → 表 → グラフ」の並び。

⚠️ **バンドの基準は「まだ届いていない一番手前のライン」**（15万位 → 10万位 → 英雄）。
全員に英雄(2000位)を当てると、下位の人は差が数百億になって判断材料にならない。
全部到達済みの人だけ英雄を基準にして余裕を見る。

- **着地予想** = いまの値 ×（前回の最終 ÷ 前回の同じ時点）。
  「同じ時点」は `day_of` と時刻で合わせる。前回に記録が無い人は `—`。
  第82回を選ぶと第81回が取れないので、着地予想は全員 `—` になる（正しい挙動）。
- **時速** は1つ前のスナップショットとの差。日をまたぐ境目も特別扱いしない。
  本戦は7:00開始なので、7時の時速は0、8時が最初の1時間ぶんになる。
  検算: 時速の合計＝日別表の「その日」＝累積の差（第83回本戦4日目のすなっで227.4億が一致）。
- 順位が深い人はgbfdataに収録されない時刻がある（ぽぬは第83回で31点のみ）。
  その日に本人の記録が無いときは、ボーダーだけの線を黙って出さずに注記を出す。

## 6. 公開（Render）

本体アプリと**同じリポジトリ `gbf-kasumi` の `koran/` サブディレクトリ**に置き、
Renderでは**別サービス `gbf-koran`** として動かす。`render.yaml` に2つ目として書いてある。

⚠️ **個人IDはコードに書かない。** このリポジトリは公開されている。
本番は環境変数 `KORAN_UIDS`（カンマ区切り）、手元は `members.txt`（gitignore済）から読む。
どちらも無いときは「追跡する人が設定されていません」と出る。

⚠️ **keepaliveは付けない。** Renderの無料枠は**ワークスペースあたり月750インスタンス時間**で、
本体アプリのkeepaliveが既に620時間使っている。2つとも起こし続けると月内に**両方止まる**。
こちらは15分無アクセスで休止し、初回アクセスに約50秒かかる代わりに、使った時間しか消費しない。
残りは約130時間＝1日あたり4時間強なので、古戦場の期間に集中して使うぶんには足りる。
