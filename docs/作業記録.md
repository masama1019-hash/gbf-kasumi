## 1. 現在の構成

| 項目 | 内容 |
|---|---|
| サーバ | `server.py`（標準ライブラリのみ / `ThreadingHTTPServer`） |
| フロント | `static/index.html` 単一ファイル（Chart.js はCDN） |
| タブ | ライブ / サーチ / 個ラン |
| データ元 | gbfdata API（`https://gbfdata.com/api`） |
| ローカル起動 | `python3 server.py` → `localhost:8930` |
| ホスティング | Render 無料プラン（512MB / 15分アイドルでスリープ、復帰約50秒） |

### 重要な制約・ハマりどころ

- **`User-Agent: Mozilla/5.0` ヘッダが必須**。素の urllib は 403 Forbidden になる。
- **`protocol_version = "HTTP/1.1"` が必須**。既定の HTTP/1.0 だと Render のプロキシが接続を
  再利用したときに `x-render-routing: no-server` で約50%が404になる。全レスポンスに
  `Content-Length` を付けること。
- gbfdata は**毎時のスナップショットのみ**保持（`07:00`〜`24:00`）。`:20` `:40` は存在しないので
  20分刻みのグラフは作れない。
- 予選の時刻表記は 20:00〜30:00（30:00 = 翌6:00）。予選は深夜も稼働する。
- **本戦は7時〜24時**。24時以降は貢献度に反映されない。
- `day_of`: 1=予選1日目, 2=予選2日目, 3=インターバル, 4〜7=本戦1〜4日目
- 個人の `point` はイベント累積、団の `today_point` はその日ぶん。
- マッチング: Day1/4=大枠、Day2/3=前日の貢献度。
- `users/rankings` の `per_page` は**500まで有効**（1000は不可）。
- ランキングの深度は約200,500位まで。
- **個人の時刻毎データを直接返すAPIは存在しない**（`/users/{uid}/histories` は日別のみ）。
  そのため時刻毎の個人順位はランキングページを走査して特定する必要がある。

## 2. 個ランの時刻毎(1H)の探索（2026-07-30）

### 表示モード

**「概要(日別)」＋「各日(1H)」の8項目のみ。** 全期間(1H)は走査量が多く負荷が大きいため
2026-07-30に**廃止**した（サーバ59行・フロント41行を撤去）。
日程に無い `day` 値（廃止した `day=all` の古いブックマークやキャッシュ）は
**概要にフォールバック**させる。これを忘れると `do` が `None` になり
`ev.get(do - 1)` で `TypeError` を返す（実際に本番で発生させた）。

### 探索アルゴリズム（`koran_hourly`）

個人の時刻毎データを返すAPIが無いので、時刻ごとにランキングページを走査して本人を探す。
段階を追って、簡単な人は早く終わり、難しい人だけ時間をかける構成にしている。

1. `users/rankings` の `per_page` を 500 に（`PAGE = 500`）。リクエスト数が約1/5。
2. **①アンカー**: 均等な5点を `max_pages=14` で先に実測（並列8）。
3. **②補間**: 残りはアンカー間の順位を線形補間して `max_pages=8` の狭い範囲で探す。
4. **③総なめ**: それでも取れない時刻は `find_user_sweep`。**履歴由来のhint近傍から
   外側へ広げ、深度上限（`MAX_RANK = 200500`）まで到達する**。
   まず数点だけ総なめして足場を作り、間は `max_pages=12` の補間で埋め、
   最後の取り残しだけ再び総なめする。
   総なめはページを**24枚ずつ並列**に見て、見つかった時点で打ち切る
   （`find_user` は1枚ずつ順に見るので、86枚目で当たる場合に86回の逐次通信になり遅い）。
5. **ページ本文を丸ごと解析しない**（`_probe_page`）。生のバイト列に `"user_id":<uid>` が
   含まれるページだけ `json.loads` する。**実測で json.loads 1.2ms 対 部分一致 0.002ms
   ＝552倍**。needleに終端文字を付けないので、別IDに前方一致して余分に解析することは
   あっても取りこぼしは起きない。
6. 探索結果を `_ufound[(raid,date,time,uid)]` にキャッシュ（再表示 2.5秒 → 0.00秒）。
   ページ単位のキャッシュは**時刻ごとにURLが変わり再利用が効かない**ので廃止した。
7. **先読み**（`prewarm_loop` / 毎時4分）で本人の**当日ぶん**を最優先で温め、`_pinned` に
   入れて他の団員を検索してもLRUで押し出されないよう保護。
   全期間の廃止に合わせて7日ぶん→1日ぶんに絞り、gbfdataへの毎時アクセスを約1/7にした。
8. **本戦(day_of 4〜7)は24時以降を走査しない**。予選・インターバルは末尾のボーダーが
   動いたかで判定して落とす（日種別の決め打ちを避け、次回開催にも自動追従）。

### ⚠️ ローカルで直っても本番で直っているとは限らない

Renderは**0.1CPU**。ローカルで無視できるJSON解析が本番では支配的コストになる。
一度「修正完了」と報告した時点で、本番では明蓮が180秒かかった上に**実測2/18**で
誤った値が出たままだった。**必ず本番のコールド状態で実測してから完了とすること。**
`scout_speed` もローカル19秒に対し本番130秒だった。

### ⚠️ 最重要の教訓: 取得漏れを直前値で埋めると「誤った数値」になる

「取れない時刻は直前値を引き継ぐ」だけの実装にすると、**取得漏れと本当の稼ぎ0が
区別されず、漏れが『稼ぎ0』として固定表示される**。

実害の例（さくらえび・本戦1日目）:

| 時刻 | 埋めて表示していた値 | 実際の値 |
|---|---|---|
| 8時 | 5.6億 / 42677位 / 時速0.0 | **11.1億 / 16536位 / 時速5.5** |
| 12時 | 5.6億 / 42677位 | **17.3億 / 11911位** |
| 20時 | 5.6億 / 42677位 | **17.6億 / 23875位** |

18時刻のうち実測できていたのは7時と24時だけで、17時間ぶんの数値を作ってしまっていた。
**異常の見分け方: 順位が何時間も1桁も動かない。** 本人が止まっていても他人が伸びれば
順位は動くので、順位が完全に同一なら実測ではない。

原因は**順位が非単調に動く**こと。さくらえびは `7時 42677位 → 9時 8338位 → 24時 34713位`。
朝に一気に伸ばして順位が3万位以上ジャンプし、その後は止まって抜かれ続ける。
順位の連続性を前提にした補間では原理的に届かない。だから③の総なめが必要。

### 初回時刻の時速

先頭を一律 0.0 にすると**誤り**。予選1日目20時は2000位が既に0.8億あるのに0.0となり、
累積グラフと時速グラフが食い違う。
`speed(cum, prev0)` で **prev0 = 前日の最終値**を「1つ前の時刻」として使う
（ボーダーは `user_border_hourly(raid, prev_date)` の最終値、本人は `base_cum`）。

| 日程 | 初回時刻の時速 | 理由 |
|---|---|---|
| 予選1日目 20時 | 0.8（=累積そのもの） | イベント開始＝0からの増分 |
| 予選2日目 7時 | 0.4 | 前日30時(=6時)から1時間ぶん |
| 本戦1日目 7時（本人） | 0.0 | 24時〜7時は稼ぎなし |

`base_cum` は**必ず `round(x, 1)` で表示と同じ桁に丸める**。丸め差で時速が `-0.0` になる。

### 最終チェックの実測（第83回・本番Render・2026-07-30）

**団（サーチ）— 全て30秒以内。** 上位100位は団ランキングの1ページ目に入るので一律に速い。

| 団（順位） | scout | 時速 | 合計 |
|---|---|---|---|
| 風花雪月(1位) | 1.66秒 | 10.36秒 | 12.0秒 |
| 雲の王国(4位)〜行雲流水(100位) | 0.5秒前後 | 0.3〜0.6秒 | 0.8〜1.3秒 |

**個ラン（時刻毎1H）— 30名中20名が30秒以内、10名が超過。データは全員18/18で正確。**

| 区分 | 例 |
|---|---|
| 30秒以内(20名) | とくこ0.5 / ジータ1.8 / Laphis3.5 / すなっ4.0 / 紅蘭10.9 / はりま25.4 / ルルフォン27.7 |
| 30秒超(10名) | ジーク30.8 / さくらえび33.8 / 明蓮35.9 / カノン48.8 / Ryan68.2 / 風色幻想75.6 / ぎのこ79.7 / きぃ103.4 / ノイン112.4 |

超過するのは**最深順位が5万位より深いメンバー**。1ページ500順位なので、
ノイン(最深116,534位)は233ページ目を18時刻ぶん探すことになる。
第83回は24/30名が3万位より深く、最深はさくらえびの190,130位。

再表示はいずれも0.00〜0.24秒（`_ufound` のキャッシュによる）。

### 検証のやり方（必ずこの2本で行う）

1. **独立した全域スキャン**（1位〜200,500位を500刻みで総なめ）で真の値を取り、照合する。
   目視やアプリ自身の出力同士の比較では、上記の「埋めた誤り」を見逃す。
2. **グラフと表の突き合わせ**: `charts['#kSpdH'].data` / `charts['#kCumH'].data` を
   ブラウザで読み出して表のセルと数値比較し、さらに「時速＝累積の差分」を検算する。

### 試して逆効果だったので戻した案（再挑戦しないこと）

| 案 | 結果 |
|---|---|
| 逐次で順位を引き継ぐ（並列を捨てる） | 全期間39.6秒 / すなっ172秒 / 単日36秒 |
| アンカーを逐次化（5点だけ） | とくこ単日66秒 / 全期間134秒 |
| 点数から順位をlog-log推定（2000位と10万位を基準） | 紅蘭が125→76時刻に悪化、単日20秒 |
| 深追いの二分探索 `find_user_deep` | 単日3.2→10.1秒、紅蘭で24時刻欠損 |
| `max_pages` を大きく取る（60など） | 単日16.7秒に悪化 |
| 総なめを `find_user`（1枚ずつ逐次）で行う | さくらえび126秒。並列化して58秒 |
| 総なめの上限を60,000位にする | 明蓮(66,000〜99,000位)が実測2/18で誤値 |
| 推定点数から順位を二分探索（`find_user_bypoint`） | ぎのこ79→118秒、さくらえび34→117秒に悪化。急に伸ばす人は点数の推定が外れる |

**教訓: 並列を捨てる案と、順位のヒント推定を凝る案はすべて悪化した。**
効いたのは「リクエスト数を減らす（per_page）」「走査対象を減らす（死に時間の除外）」
「先読み」「見つからない場合に総なめへ切り替える」。

## 3. 全体の応答高速化（2026-07-30）

Renderは0.1CPUなので、**リクエスト数と往復回数そのものを削る**のが効く。

| API | 改善前 | 改善後 |
|---|---|---|
| `/api/config`（開いた瞬間に必ず待つ） | 5.41秒 | 0.69秒 |
| 予選 | 25.08秒 | 4.74秒 |
| サーチの時速(`scout_speed`) | 130.24秒 | 3.75秒 |

効いた対策:

1. **ページ取得の並列化**（`pages()`）。`guild_histories`(7ページ)と
   `user_histories`(6ページ)を1枚ずつ待っていた。
2. **団ランキングも `per_page=500`**。個人側だけ500にして団側は50のままだった。
   `find_guild` の歩幅も500にしてページ数が約1/10。深度は約20,500位まで。
3. **`hourly_series` の並列化**。17時刻を1つずつ順位を引き継ぐ完全逐次だった。
   取れなかった時刻だけ実測値の平均を起点に取り直す。
4. **予選の同時実行**。今回と前回オーバーレイは独立なのに直列だった。
   1タスク内の2通信（300位ボーダーと自団）も同時化。
   さらに300位ボーダーの `get` に **`ttl` 指定が漏れて既定180秒**になっており、
   確定した過去回でも毎回取り直していた。
5. **取得失敗のキャッシュ**（`NEG_TTL = 600`）。失敗はキャッシュされず毎回再取得していた。
   予選1日目の19時はgbfdata未収録(**HTTP 404**)で、これだけで毎回13リクエスト・6.5秒。

⚠️ 5の対応で `19:00` を時刻名で除いたら、**2日目には実在する19時まで落として1時刻失った**。
軸のために合成した時刻かどうかで判定すること（`t in real`）。

## 4. Renderの休止対策（キープアライブ）

無料プランは15分アクセスが無いとスリープし、次のアクセスに約50秒かかる。
`.github/workflows/keepalive.yml` がGitHub Actionsから10分間隔で静的ページを叩く。

**稼働は JST 05:00〜翌01:00 の20時間に絞っている。**
無料枠は「ワークスペースあたり月750インスタンス時間」で、24時間だと31日の月で
**744時間**となり余裕が6時間しか残らない。他に無料サービスがあると月内に全部止まる。
20時間なら月620時間で余裕130時間。本戦(7〜24時)は完全にカバーし、予選の深夜も1時まで。
24時間にしたい場合は cron を `*/10 * * * *` に変える。

- 叩くのは静的ページのみ（gbfdataへは問い合わせない）。
- GitHub Actionsのスケジュールは**ベストエフォート**で数分〜十数分遅れることがある。
- **リポジトリが60日間無活動だとGitHubがスケジュールを自動停止**する
  （何かpushするか手動実行で復活）。

## 5. メモリ超過(OOM)の対処

Renderから「exceeded its memory limit」通知。原因は `_cache` に上限がなく、
期限切れも掃除していなかったこと（1件38KBのランキング応答が蓄積）。

- `CACHE_MAX` + `_cache_put` でのLRU削除
- `slim=` で保存前に応答を間引く
- `per_page` と TTL の調整

現在は上限約200MBで頭打ち（512MB枠の約40%）。`_pinned` は `PIN_MAX = 600` で上限を持つ。

## 6. 主なUI仕様（ユーザー指定）

- 日程名は全て「予選1日目 / 予選2日目 / インターバル / 本戦1日目〜4日目」で統一。
- カード色: 自団=薄い青 / 相手=薄い赤 / 英雄(2000位)=薄い赤 / 10万位=薄い緑（`.metric` 系）。
  これは**予選タブと個ランタブのカード**の話。本戦ライブのカードは第7章の判断バンド＋ストリップに置き換えた。
- グラフの凡例は**Chart.jsの箱を使わず、`mkChart` がデータセットから自前のチップを生成**して
  グラフ直前に差し込む。線種(実線=今回 / 破線=前回)まで見せたいため。
  見出しに「青=霞桜団」のような色の説明は書かない（チップと重複する）。
- 並び順: 当日貢献度 → 時速 → 参考情報 → 総合順位の推移。**勝率予想は最後**。
  カード内も素の数字（貢献度・時速・型）を先に置き、そこから導かれる判断（リード→勝率）を後ろにまとめる。
- 勝率は厳しめ（`ratio_winprob` の指数k=3.5。団1位級の比0.13で1%未満）。
- 本戦1・2日目は勝敗が付いたら抑える（翌日のマッチングと戦力温存のため）助言を出す。
- 時刻表示は**日付が変わったら1時〜に戻す**（`hour_label()` が 25:00→「1時」に変換）。
  予選の25〜30時表記はやめた。24:00 は「24時」のまま（0時にしない）。
- 見出し「時速（億・1H）」「(日程)（億単位）」。全期間モードは廃止したのでその見出しも無い。
- 個ランの表示モードは「概要(日別)」＋「各日(1H)」。**全期間(1H)は廃止**。
- 表に「—」を並べない。ただし**取得漏れを直前値で埋めてはいけない**（第2章の教訓）。
  実測がまだ無い先頭は0で埋める（順位だけは架空の値を入れず空欄のまま）。
- 自動更新のラベルは「**自動更新**」。gbfdataの毎時更新に追従（毎時3分、失敗時は3分おきに5回まで）。
  操作列のチェックは `.chks` で1グループにまとめる。個別に折り返すと「撤退済み」だけが次行へ落ちる。
- 開いた日の日程を自動選択。
- 団チャット通知用のコピペ文を最下部に出す（本戦・予選それぞれ）。
- **相手団の団員一覧**（サーチ）: `/guilds/{gid}/members` が公開団のみ団員別貢献度を返す。
  非公開団は404なので `guild_members()` は `None` を返し、その場合は一覧を出さない。
  上位団ほど非公開が多い。
- **前日の比較**に自団・相手団それぞれの**団総合順位**も出す。
- **最高時速をハイライト**する（`.mx` = 赤字＋太字＋薄いオレンジ地）。
  ⚠️ CSSは `.sp`（灰色）を `.mx` より**前**に書くこと。後ろに書くと打ち消される。
- **面の塗りは「主役の系列」だけ**（`ds.area` を指定したものだけ `mkChart` が
  グラデーションに変換する）。⚠️ 相手やボーダーまで塗ると、接戦のとき
  （自団377.5億 対 相手373.1億など）**2枚の半透明が全面で重なって灰色に濁る**。
  予選は差が大きいので気づきにくく、本戦で初めて出る。
- 棒は角丸＋隙間つきのグラデーション。⚠️ **下端まで透明に抜くと深夜帯の低い棒が消える**ので
  `b8` で止める。
- 線の終端に系列名と最終値を直接置く（`ds.endLabel`）。近い札は自動で上下に押し分ける。
  時速と順位のグラフには付けない（最終点が特別な意味を持たないため）。
- 罫線は横だけ・極薄（不透明度3.8%）、目盛りは4本。ツールチップは濃紺の角丸カード。
- **予選の参考テーブル**: 過去6回の300位ボーダー・属性（「水有利」形式）・開催曜日・
  前回比の上昇率・当団の予選順位と貢献度。6回平均は参考にならないので出さない。
- 比較ラインの選択順は **両方 / 10万位 / 英雄(2000位)**、既定は「両方」。
- 個ランのグラフは**実線に統一**。予選タブの前回開催オーバーレイのみ破線。
- **前回オーバーレイは本色＋破線**。⚠️ 淡色（`#85B7EB` / `#F0997B`）は使わない。
  彩度0.092で下限0.10を割って**グレーに見え**、背景コントラストも2.05/2.14と
  基準3.0未満で**読めていなかった**。コントラストを保ったまま白へ寄せられるのは
  10〜16%までで本線と区別が付かないため、**色ではなく線種で区別する**。
  主要2色（`#378ADD` / `#D85A30`）と個ランの3色（＋`#1D9E75`）は検証を通っているので据え置き。
- 時速は**縦棒グラフ**（折れ線より増減が読みやすい）。見出しは最高/平均のミニタブに追従。
- 勝率目安は**本戦の日ごと**で比較する（総貢献度どうしの比較ではない）。
  補足文の「上回った回数」も同じ日ごとの集計に揃えること（以前は本文と数え方が食い違っていた）。

## 7. 本戦カードと順位表示（2026-09-03に作り直し）

### 判断バンド＋数値ストリップ

毎時見るのは「**勝っているか・どうすべきか**」なので、リード・勝率・推奨アクションを
**1枚の判断バンド**にまとめて最上部に置き、素の数字は下の細いストリップへ落とす。
バンドは主役なので余白と字を大きく取る（高さ約204px、リード40px、勝率32px）。
推奨アクションの本文は補足色ではなく**本文色**。実際の指示にあたるため。

ストリップは**2枚に分ける**。1枚に7枚を流すと6+1で折り返して灰色の空きが出る。

| | 中身 |
|---|---|
| 上段 | 最高時速×2 ／ 前日同時刻比×2（数値） |
| 下段 | 相手の方針 ／ 時間帯パターン×2（型・方針。バーを置くのでセル幅を広めに） |

⚠️ ストリップは**セルの高さが揃わない**（パターンはバーぶん高い）。値を上に置くと
時速セルだけ余白が下に残るので、`.strip .v { margin:auto 0 }` で空きの中央に置く。

⚠️ セレクタは `.strip > div`（直接の子）にすること。`.strip div` だと内側のバーにも
padding と background が乗り、**バーが潰れて灰色の隙間になる**。

### ⚠️ 最高時速は表とカードで別々に計算しない（2026-09-03に食い違いが発覚）

カードの「本日最高時速」が、表で強調している最大値と**違う値を出していた**
（表は8時の50.9を最大と示すのに、カードは9時の49.9を表示）。

原因は `peak()` が**8時を意図的に除外**していたこと。
「8時は日始からの累積なので1時間ぶんではない」という前提で書かれていたが、
**本戦は7時開始**なので8時のスナップショットは 7→8時のちょうど1時間ぶん。
除外する理由がなかった（予選も19時開始→20時が最初なので同じ）。
表側は `mxOf` で全時刻を見ていたため正しく、カードだけがずれていた。

→ 8時を含めたうえで、**表の強調をカードのピークと同じ値から作る**。

```js
const opk=peak(os,H), ppk=peak(ps,H);
const mxOs=opk.v, mxPs=ppk.v;   // 別々に求めるとまた食い違う
```

同じ数字を2箇所で別々に計算しない。片方だけ直して食い違う事故は自分では気づきにくい。

### 時間帯パターンの凡例

バーの下に `朝36% 昼23% 夕21% 夜21%` を出す。％を付けても下段ストリップの
セル幅（170px）に1行で収まる。

### 状態色 —「悪い」を赤にしてはいけない

`.bad` は `--red`（`#D85A30`）＝**相手団の色と同一**。そのため自団カード（青地）の
最高時速が赤字で出て、相手の数字と紛らわしくなっていた。

相手の赤と見分けが付く赤を探したが**存在しない**（`#B4523A` ΔE7.4 ／ `#A32D2D` 14.8 ／
`#B26A00` 8.4。いずれも基準15未満）。緑は26.2で明確に区別できる。

→ **良い＝緑、悪い＝色で示さず「▼」と語と濃いインク**。カード内ではこれを使う。
表の `.bad` はそのまま（表には相手色が無いので衝突しない）。

### 総合順位は折れ線ではなくマス目

自団は **112〜423位で3.8倍動く**のに、0〜4000位の等間隔目盛りでは軸の**8%**に潰れて
真っ平らにしか見えなかった。順位は「100位と200位」と「3000位と3100位」で意味が違うので、
等間隔だと下位側だけが誇張される。「0位」という存在しない目盛りも出ていた。

→ **順位帯のマス目**（`rankHeatHtml`）。ライブ・サーチの両方に適用。

| 帯 | 色 | 文字 |
|---|---|---|
| 〜10位 | `#4A0F06` | 白 |
| 〜100位 | `#8C2317` | 白 |
| 〜300位 | `#C1503A` | 白 |
| 〜500位 | `#E09872` | 濃紺 |
| 〜1000位 | `#F2E3D6` | 濃紺 |
| 〜2000位 | `#8FB4D4` | 濃紺 |
| 2000位超 | `#1F4E79` | 白 |

**上位ほど赤・下位ほど青**（ユーザー指定）。3000位超はまず当たらないので上位側を細かく刻む。
隣接帯のΔEは15.0〜34.2（基準15）、文字は地の明るさで白/濃紺を出し分け最小4.69を確保。

⚠️ `api_scout` の `rank_history` だけ `raid` を返しておらず、開催回の見出しが
「**第undefined回**」になっていた。ライブ側と形を揃えること。

### 配色を変えるときは必ず数値で確かめる

dataviz スキルの `validate_palette.js` を**Pythonへ移植**して使っている
（この環境に node が無いため）。閾値と行列は原典のまま。

- 色覚多様性での分離 ΔE >= 8（隣接ペア）、通常視 ΔE >= 15
- 彩度 >= 0.10（下回るとグレーに見える）
- 背景コントラスト >= 3.0

主要2色（`#378ADD` / `#D85A30`）と個ランの3色（＋`#1D9E75`）は検証を通っている。

## 8. ファビコン（Safariでハマった）

`static/favicon-sakura.ico` = **48×48のPNGを収めたICO**。桜のデザイン（地 `#FBD9E4` / 花弁 `#B4587C`）。
`apple-touch-icon` に `favicon-48.png` も置いている。

| やったこと | 結果 |
|---|---|
| SVGのdata URI | ❌ **SafariはSVGファビコンに未対応** |
| PNG/ICOを実ファイルで配信 | 拡張子→Content-Type の対応表(`CTYPES`)が必要 |
| BMP形式のICOに変換 | 不要だった。PNG-in-ICOで動く（ytmp3.gl が実例） |
| ファイル名を変えて配信 | Safariのキャッシュ回避に有効 |

⚠️ **Safariはファビコンを「アイコンのURL単位」でキャッシュする**（`~/Library/Safari/Favicon Cache`）。
サーバ側が正しくても、お気に入りに登録済みだと古いアイコン（地球儀）が出続ける。
このキャッシュはmacOSのTCCで保護されていて**コマンドラインから消せない**（`Operation not permitted`）。
**ファイル名を変える**のが実質的な回避策。

## 9. 個人ボーダーの過去データ（`GW_BORDER_FINAL`）

gbfdataは**個人ボーダーを第82回以降しか収録していない**。それ以前の回を選んだときに
「参考: 直近6回の着地」が全て「—」になるので、GameWithの記事から抽出した値を埋め込んでいる。

- 出典: `グランブルーファンタジー.gamewith.jp/article/show/91154`
  （punycodeホスト `xn--bck3aza1a2if6kra4ee0hf.gamewith.jp`）
- 収録: **第48〜83回の36回分**（欠番なし）。開催回セレクタは自団の参加履歴から作られ
  第63回まで遡れる。`koran_past3` はその6回前まで見るので第57回まで必要になる。
- 検証: 抽出値が既存の手入力7回分（77〜83回）と**完全一致**。82・83回はgbfdataの実値とも一致。

⚠️ **勲章の順位帯は時代で変わる**ので、2000位以外をそのまま横並びにしてはいけない。

| 回 | 勲章の最上位帯 |
|---|---|
| 83〜77回 | 10万位 |
| 76〜68回 | 9万位 |
| 67〜57回 | 8万位 |
| 56〜50回 | 7万位 |
| 49回以前 | 5万位 |

**2000位【称号】だけは全回共通**なので、第76回以前は2000位のみ収録している。

### 記事を解析するときの注意

- **WebFetchは要約で数値を壊す**。生HTMLをcurlで取ること。
- 数値の正規表現は `(\d{1,3}(?:,\d{3})+)` とカンマ区切りで縛る。`[\d,]+` だと直後の
  前回比パーセントまで飲み込んで「502305.3億」のような値になる。
- 1回のブロックに「本戦終了時点」「本戦3日目終了時点」…と複数の表が並ぶ。
  **見出しがある回と無い回がある**（第80回=あり、第63回=なし・表が直接続く）。
  `本戦終了時点` があればそこから、無ければブロック先頭から**最初の2千位**を拾えば両方正しい。
- 切り出しの終端は `予選までのボーダー` / `予選終了時点`。単に「予選」で切ると
  第80回のように本戦の表ごと落ちる。
- 第49回だけ「1〜3日目時点」の途中経過が別ブロックで並ぶので除外する。

### ⚠️ 古い回で日程を選ぶと500エラーになっていた（2026-08-24修正）

gbfdataが個人ボーダーの時刻毎データを持たない回では `koran_hourly` の `times` が空になる。
`n = max(1, len(times))` が 1 を返すため `times[0]` を見に行き `IndexError` で落ちていた。
呼び出し側には「この日の時刻毎データはgbfdataに未収録です」を返すガードが既にあるので、
**空のまま早期リターン**させて本来の経路に乗せる（全時刻の空振り走査も省ける）。

## 10. 撤退フラグ（本戦の推奨アクション）

本戦の「推奨アクション」は勝率と時間帯パターンから出すが、**団として撤退したあとは
勝敗の話をやめて撤退後の指針に切り替える**。撤退は団の意思決定なので自動判定できない。

### なぜサーバ側に持つか

最初はブラウザの `localStorage` に持たせたが、**押した人の画面でしか切り替わらない**。
団員が開くと「継続」と出たままで、周知の用を成さない。
そこで状態はサーバが持ち、切り替えは団長だけができるようパスワードで照合する。

- 切り替えは `POST /api/retreat` のみ（`{raid, date, on, pw}`）
- 照合は `hmac.compare_digest`（時間差から推測されないように）
- **パスワード未設定なら誰も切り替えられない**側に倒す（503）
- キーは `開催回|日付`。本戦は1日1試合なので相手名は要らない

### 保存先

Renderの無料プランは15分アイドルで停止し、書いたファイルは消えるので、
永続化はGAS経由でスプレッドシートのセル1つ（JSON）に行う。

⚠️ **保存先は開催回ごとに作り直す記録用シートではなく、恒久的なシート（団員DB）を指すこと。**
キーに開催回が入るので1枚で全開催回を賄える。記録用シートを指すと開催回ごとに
環境変数を張り替える羽目になる。

パスワード・GASのURL・スプレッドシートIDは**公開リポジトリに置けないので全て環境変数**。

| 変数 | 用途 |
|---|---|
| `RETREAT_PW` | 切り替えのパスワード。未設定なら誰も切り替えられない |
| `GAS_URL` | GAS Web App の `/exec` |
| `GAS_SSID` | 保存先スプレッドシート（**恒久的なもの**） |
| `GAS_SHEET` | タブ名（既定 `撤退`）。**タブが無いとGASが sheet not found を返す** |

### 文言の方針（ユーザー指定）

**撤退後はフリーランで、抑制を強制しない。** 効くという事実だけ伝えて判断は各自に委ねる。

⚠️ **貢献度マッチングが効くのは本戦2日目・3日目**なので、前日を抑える意味があるのは
**本戦1日目・2日目だけ**。本戦4日目のマッチングは大枠で決まるため、3日目に抑えても
翌日の相手は変わらない（`MATCH_BY_YESTERDAY`）。ここを取り違えると嘘の助言になる。

| 日程 | ラベル | 中身 |
|---|---|---|
| 本戦1・2日目 | 撤退済み・自由行動 | 自由行動と先に伝え、「余裕のある方だけ」抑えると翌日が楽になると補足 |
| 本戦3日目 | 撤退済み・個人優先 | 抑える必要は無い。余裕のある方は体力温存で4日目に備える |
| 本戦4日目 | 撤退済み・個人優先 | 翌日が無いので出し切ってよい。無理のない範囲で |

同じ理由で、**撤退していない側の3日目**も「Day4に温存」から改め、マッチングに
影響しない旨を明記している。閾値（勝率85%以上で抑え／15%以下で撤退）は据え置き。

## 11. 開催回が変わったときの手順

**Webアプリは何もしなくてよい。** `server.py` に開催回の固定値は無く、開催回の一覧は
gbfdataの自団履歴と最新回から毎回組み立てるので、新しい回が始まれば自動でタブに増える。

手を入れるのは記録まわりだけ。

1. **記録用スプレッドシートを複製**して新しい回のものを作り、データをクリアする
   （数式・見出しは残す）。
2. **`bin/honsen_record.py` の `SSID`** を新しいシートのIDに更新する。
   ⚠️ **忘れるとエラーにならず、新しい回の記録を前回のシートに書き込む。**
   `RAID_OVERRIDE = None` で開催回自体はgbfdataから自動追従するので、ここだけが穴。
3. **`yosen_state.json` をリセット**する。前回の貢献度が残っていると、
   予選Discordの重複防止（自団貢献度の単調増加で判定）が働いて発表が抑止される。
4. **団員の入れ替えがあれば `MEMBERS` と団員DBを更新**する（名簿は加入順に並べる。既存者の貢献度が列ズレしていないか名前ごとに全列照合すること）。

`GAS_SSID`（撤退フラグの保存先）は恒久シートを指しているので**触らない**。

## 12. 運用メモ

- **pushは変更ごとに内容を報告して承認を得てから**行う（ユーザー指定）。
- 認証は専用のSSH鍵（`~/.ssh/config` の Host github.com で指定済）。
  **トークン・パスワード・認証コードは扱わない**（ユーザー自身が操作する）。
- リポジトリは**公開**なので、GAS Web AppのURL・団員の個人ID・スプレッドシートID・
  メールアドレスは絶対にコミットしない（push前に `git diff` で確認する運用）。
- 画面からファイルを直接アップロードすると、ローカルとリモートが分岐して push が
  拒否される。その場合は `git fetch` → 内容を確認 → `git reset --soft origin/main` →
  再コミットで、リモート履歴を消さずに最終版を載せられる。
- 次回（第84回）は開催が始まれば自動的にタブに追加される。
